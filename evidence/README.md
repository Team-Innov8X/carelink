The allocator and its model are implemented in TypeScript from scratch; they use no pretrained model and make no external AI/API calls. CareLink's separate configurable triage-chat integration is outside this simulation and does not affect allocation.

## Setup and commands

Use the repository's Node/npm environment and install the lockfile dependencies:

```powershell
npm ci
```

The simulation commands below run locally and need no database or AI credentials. To run the wider CareLink application, configure the values in `.env.example` as needed, then run `npm run dev`.

```powershell
npm run gen-data
npm run train
npm run eval -- --split validation --episodes 300
npm run eval -- --split test --episodes 300
npm run test
npm run dev
```

`gen-data` writes the synthetic splits. Set `HLTH02_SEED` to override its default world seed. `train` reads training and validation data only and refuses to overwrite a recorded test evaluation. Evaluation requires an explicit split. Validation evaluation writes `evidence/validation-results.*`. The test command above is the **single permitted test replay run**; it requires at least 300 episodes and refuses existing or previously locked test results. Do not run it again to reproduce the test numbers. `npm run test` runs Vitest; `npm run dev` starts the Next.js app, including `/surge-demo`.

## Data, schemas, and split

All data is generated by `sim/world.ts`, with assumptions documented in `data/synthetic/assumptions.md`. The default world seed is **20261011**. It creates 50 minute-resolution days for four synthetic hospitals and two resource types (`icu_bed`, `emergency_bed`), with synthetic admissions, stays, walk-ins, surges, closures, and resource losses. `sim/generate.ts` serializes the world through `sim/dataset.ts` into:

| File | Days | Contents |
|---|---:|---|
| `data/synthetic/train.json` | 1–30 | `seed`, `split`, `days`, `samples`, and training-only completed-stay duration distributions |
| `data/synthetic/val.json` | 31–40 | `seed`, `split`, `days`, and `samples` |
| `data/synthetic/test.json` | 41–50 | `seed`, `split`, `days`, and `samples` |

The split is strictly chronological: **train 1–30, validation 31–40, test 41–50**. `SimDay` contains its day number, hospital/resource timelines, and hidden synthetic replay events. Each `HospitalDay` includes ground-truth free-unit, operational-capacity, and open/closed timelines, as well as decision-time observed occupancy, known capacity, availability, walk-in arrivals, and admission times. `DecisionSample` contains an ID, day/minute, hospital, resource type, ETA, units needed, decision-time features, and a binary label. Its features include current availability and occupancy, recent walk-ins, time/calendar fields, resource type, closure state, and current-stay elapsed times.

The label is **1** exactly when the raw ground-truth free-unit timeline at `decision minute + ETA` has at least `unitsNeeded` units, otherwise **0**. An arrival beyond that day's 1,440-minute timeline is labeled 0. Features are constructed from decision-time observations and the completed-stay distribution from training days only; future events and future free capacity are not model inputs. `tests/labels.independent.test.ts` independently re-derives each label from the raw ground-truth timeline for all 50 days. It does not call model or engine code.

The default generation seed is 20261011. Reproducibility and additional fixed seeds are recorded in `data/synthetic/assumptions.md`, `sim/world.ts`, and the tests. The independent label test uses 20261010; the ledger fuzz test uses 20261013. The frozen replay evaluation uses episode seed **20261020** and paired bootstrap seeds **20261013**, **20261014**, and **20261015**. The six scenario inputs are derived from validation-day replay material (days 31–40), not from test episodes; their JSON files record seeds and inputs.

## Model, predictions, and allocation policy

`model/model.json` identifies a **custom L2 logistic regression**, implemented in TypeScript and trained from scratch on days 1–30. Lambda was selected using validation days only; the saved value is **0.001**. The model estimates the probability that the required free capacity will exist at arrival. Its saved feature order, means, standard deviations, weights, intercept, training period, seed, training-only stay durations, and runtime versions are in that file. It was not pretrained and makes no API calls.

`model/predictions.csv` stores validation and single-run test predictions as `sample_id, features_hash, p, label, split`. `model/parity-vectors.json` stores validation vectors used to check runtime parity. `model/metrics.json` contains sample-level Brier score, calibration, accuracy, and other metrics. On the test sample prediction task, model Brier was 0.0738 and baseline Brier was 0.0933. The log-loss values are not a fair comparison because the baseline emits hard 0/1 probabilities.

The baseline is current-capacity-only. The model-aware allocator combines its availability probability with travel cost using `travel minutes + (1 - p_available) × 25 minutes`. The engine processes patients greedily in urgency order (urgency weights 100, 10, 1), then waiting time and patient ID. For each patient it picks the lowest-cost currently feasible hospital, with rejection rate and hospital ID as tie-breakers. This is a **greedy heuristic, not a globally optimal assignment solver**; an earlier choice can affect later patients and the engine does not search all joint assignments.

Policy constants are in `lib/allocation/constants.ts`: reroute penalty 25 minutes, ETA re-plan threshold greater than 10 minutes, and at most two reroutes per patient. An exhausted re-plan or repeated arrival failure returns `handover_failed`. These constants were frozen before the one-shot test replay.

## Replay result and interpretation

`evidence/results.json` and `evidence/results.md` contain the one-shot paired replay evaluation: 300 episodes, 3,437 patients, test days 41–50, episode seed 20261020. Both methods used identical episode inputs and pre-drawn random values.

The result is **null for a demonstrated end-to-end advantage**: first-choice handover success was 55.46% for baseline and 55.51% for model-aware; reroutes and mean handover time were nearly equal. The paired 95% episode-bootstrap intervals for success, reroutes, and mean handover time all include zero. The model-aware urgency-1 failure rate was slightly higher (31.91% vs 31.74%). The model's better sample-level Brier score did not establish better replay outcomes. Incompatible allocations and double-counted reservations were both zero for both methods.

The replay assigns and re-plans with the simulation engine. Its reservation ledger transitions are `proposed → requested → confirmed → arrived → handed_over` on success. Rejection, expiry, loss, arrival failure, cancellation, and re-planning are recorded through terminal or subsequent reservation states. The production adapter maps simulation types to existing production types, but the replay itself does not create production holds.

The engine returns only these unserved reason codes: `no_compatible_resource`, `no_capability_match`, `capacity_exhausted`, `hospitals_closed`, `displaced_by_higher_priority`, `rejected_no_alternative`, `handover_failed`, and `travel_time_limit`. The first, second, and last are each directly covered by engine tests; re-planning and capacity reasons are covered by engine and scenario tests.

`data/scenarios/S1.json` through `S6.json` contain seeded inputs and expected paired outcomes. These demonstrations are drawn from validation days 31–40, with declared scenario overrides for capacity, rejection, resource loss, duplicates, fallback, and closure. `evidence/replay-logs/S1.jsonl` through `S6.jsonl` preserve the replay records. The public demo at `/surge-demo` reads these synthetic scenario files; it does not read live hospital capacity or write real holds.

See [`limitations.md`](limitations.md) for the generator-calibration caveat, censored-stay limitation, and a concrete test-run case where model-aware handover success was worse than baseline.

## Requirements intentionally skipped

The live Mongo-backed `POST /api/allocate-batch` endpoint was not implemented. The specification labels it a should-have and puts it first in the cut list. The Phase 5 demo remains simulation-only and uses the in-memory reservation ledger; it does not call the production hold service.
